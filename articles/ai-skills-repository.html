Generating an AI Skills Repository for Your Team

Oct 31, 2026 · Andrei Stanescu · 6 min read

A year ago, every engineer on my team used AI assistance differently. Some had personal prompt collections saved in Notion, others had text files buried in their home folders, and the most effective workflows lived entirely in people’s heads. Two engineers could ask the same assistant for the same task and get wildly different results, and the difference was invisible tribal knowledge. This post is about how we turned that scattered know-how into a shared AI skills repository: a versioned, reviewed, team-owned library of prompts and skills that has become one of the most valuable assets we’ve built.

What we mean by a “skill”

For us, a skill is a named, documented, reusable unit of AI workflow. Sometimes it’s a prompt template, sometimes a rule file the assistant always loads, sometimes a small script paired with instructions. The content varies: how we structure a .NET microservice, our conventions for writing tests, the checklist the assistant should walk through before proposing a refactoring, how we want PR descriptions generated. What makes it a skill rather than a prompt is the packaging: it has an owner, a version, a purpose, and a place in a repository everyone can see.

The distinction matters because prompts are personal and skills are institutional. A prompt helps one engineer today. A skill encodes the team’s judgement so that the next engineer, or the same engineer six months from now, doesn’t have to rediscover it.

The anatomy of a good skill

We didn’t get this right on the first attempt. The skills that survived and earned adoption share a shape, and it’s worth spelling out because most prompt collections online don’t have it:

• Context: when to use the skill, and just as importantly, when not to.
• Instructions: explicit steps, not vibes. If the skill says “make it clean”, it will produce whatever “clean” means to a language model this week.
• Constraints: our standards, naming rules, patterns we forbid, quality gates the output must pass.
• Examples: links to real code in our repositories, not generic samples. Few-shot examples from our own codebase are the single highest-leverage part of every skill we have.
• Metadata: an owner, a last-reviewed date, and the problem the skill solves.

How we bootstrapped it

The repository started with a harvest. We ran a session where everyone dumped their personal prompts, notes, and habits onto a shared board, then clustered them by workflow. The first surprise was the duplication: five people had independently solved the same code-review-summary problem in five different ways. The second surprise was the gaps: nobody had written down our most valuable knowledge because it felt obvious to the people who held it.

We picked the five most repeated workflows and turned those into the founding skills, written properly with the anatomy above. Five was deliberate: enough to demonstrate value, few enough that we could hold a quality bar. Everything else waited in a backlog until it earned a slot. That backlog became our roadmap, and the rule that a new skill must replace or absorb an existing one kept the library from becoming a junk drawer.

Treat it like code, because it is code

Once the repository existed, the practices were obvious because we already had them: skills change through pull requests, they go through review, they have owners, and they get deprecated rather than deleted. A prompt that encodes a design decision is a historical artifact; six months later, being able to read what the team believed and why is worth more than a tidy folder.

The review standards apply to skills with one addition: a skill change must be exercised before approval. We don’t merge prompt edits based on how they read; the author runs the skill on a real task and links the output. Skills that nobody can demonstrate working don’t ship, and skills that rot get flagged by their last-reviewed date.

Making it stick

A library nobody uses is just well-organised neglect. Three things drove adoption for us. First, the skills are wired into the tools: the assistants load the relevant rules automatically, so using the library is the default rather than a lookup. Second, onboarding runs through it: new engineers read the skills repository in their first week, which doubles as the fastest tour of “how we work here” that we’ve ever had. Third, we made contribution visible and rewarded: the engineer whose skill gets absorbed by the whole team gets the same recognition as the author of a core service.

Anti-patterns we learned the hard way

• The prompt graveyard: skills that nobody trusts or maintains. The last-reviewed date exists to make this visible instead of silent.
• Mega-skills: one giant prompt that tries to do everything. They’re brittle, and when output quality drops nobody knows which instruction caused it.
• Hoarding: when an engineer’s private prompts are better than the shared ones, that’s an incentive problem, not a tooling problem. We fixed it by making repository contributions a visible achievement, not an extra chore.
• Copying skill libraries from the internet wholesale. Borrowed conventions teach the assistant someone else’s standards. Start from your own code and your own problems.

The measurable outcomes: consistency. Two engineers asking for the same class of help now get answers grounded in the same standards, which is a large part of how we doubled our PR rate without doubling our review burden. The unmeasurable but more valuable outcome: the repository has become the clearest written expression of what this team believes good engineering looks like. That’s not a prompt collection anymore. That’s culture, in a format an assistant can read.
